## L0
软著三件套命名有英文变体，关键词过滤必漏；图引断链检查必须剥角括号。

## L1
### 事件（2026-08-28，第 18 轮巡检）
1. **#6 物流三件套全英文命名被漏检**：patrol 的 mat_hits 用中文关键词（软著/说明书/源代码文档）+ `SOFTWARE_MANUAL.MD` 精确匹配，测得材料=0；
   而磁盘上是 `SOFTWARE_COPYRIGHT_MANUAL.md`(1552行)/`DESIGN_DOCUMENT.md`(470行)/`SOURCE_CODE.md`(3271行)。
   TL 已据此完成交付收口，差点被我按「停滞/缺材料」误判。这是 #8 知识产权
   `SOFTWARE_MANUAL.md` 教训（宽口径 find 才定位）的扩大版。
2. **同轮另一脚本重犯 r12 角括号错**：媒体项目图引写成 `![..](<../screenshots/x.png>)`，
   不剥首尾 `<>` 就查存在性 → 报「23/22 断链」假警报；剥掉后 23/23+23/23 全解析。

### 规则
1. **材料检测两段式**：先按关键词命中；对材料计数=0 但项目已近交付（截图≥20、测试报告在盘、
   TL 有收尾言论）的，必须宽口径兜底——凡 .md 名含 `manual|设计|design|源代码|源码|源程序|
   source|code|软著|copyright`（大小写不敏感）即列出行数人工归类，行数特征（说明书≥1500、
   源代码文档~3000、设计说明书数百）可辅助配对。
2. **图引解析**：提取 `!\[[^\]]*\]\(([^)]+)\)` 后必须 `.strip()` → 剥成对首尾 `<>` →
   去 `?query`/`#anchor` → 相对文档所在目录 resolve，再判存在。每条新写的检查脚本都要带这四步。
3. **TL 口径 ±1 行属换行计数惯例差**（`txt.count("\n")` vs `+1` vs `wc -l`），逐项 ±1 不判虚报；
   结构性差异（文件名、张数、断链数）才启动双测复核。
4. 巡检判定「材料=0 → 停滞/缺编排」前，先过一遍规则 1；误把已交付项目判停滞会触发错误的
   用户通知或干扰性指令。
