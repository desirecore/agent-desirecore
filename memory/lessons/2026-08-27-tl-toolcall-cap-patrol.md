## L0
编排型 run 会被「连续 100 次工具调用」上限自动停止（记 LLM_API_ERROR 但非限流）；判活别信目录 mtime。

## L1

### 现象
长编排 run（写文件循环、Sleep+轮询式监控）易撞每请求 100 次工具调用上限被终止，状态转 idle，
但磁盘产出可能仍在增长——**被打断的是编排动作（下一批没人派发），不是开发侧**。
只看文件增长会漏判"编排层已死"这一整类风险。

### 判活三口径（一起用，按可靠性排序）
1. `runs/<id>/messages.jsonl` 内消息的 `timestamp` 字段（目录/文件 mtime 不可信）
2. `runs/<id>/pending.json` mtime（长轮次内 1–2 分钟刷新）
3. 项目目录单文件 mtime 分布 + 文件名语义（区分"写页面"与"磨 mock 层"）

### 恢复被打断编排者（验证有效的模板要点）
- 明确告知"你的 run 被上限停止，产出没丢"，避免从头重跑
- 先 `ls` 核现场再决定，不重做已完成批次
- **单次 run 只做「核实 + 派一批 + 验一次收」**，验证合并成一条批量命令
  （如 `find ... | xargs wc -l`），这是防再撞上限的关键约束
- 分批派单、每批产文字摘要重置计数；`Sleep(300)` 代替多次 `Sleep(60)`
- 结尾写"不用回这条消息，直接继续推进"，省掉一次无意义往返

### 附带教训
判额度/限流不要 grep `quota/429/balance` 关键词——业务 mock 数据里大量含这些词，会大面积误报；
以 `errorCode` 与 system 消息级别核对为准。
