## L0
巡检多 Agent 项目必须查「TL 是否被 100 次工具调用上限打断」，目录 mtime 判活不可信。

## L1

### 事实（2026-08-27 第 2 轮软著巡检实测）
10 个技术总监里有 3 个（TD2/TD4/TD5）的 run 被系统以
「已连续执行 100 次工具调用仍未完成任务，已自动停止」终止（errorCode 记为 `LLM_API_ERROR`，
但**不是额度/限流问题**），状态转 idle。磁盘代码仍在涨（开发在写），所以只看文件增长会
漏判「编排层已死」这一整类风险 —— TL 一死，下一批页面就没人派发。

### 三条判活口径（按可靠性排序，全部要一起用）
1. **`runs/<runId>/messages.jsonl` 内每条消息的 `timestamp` 字段** —— 这是真活动时间。
   目录/文件 **mtime 不可信**（同一轮里 mtime 可停在 3 小时前，而内嵌 timestamp 只差 1 分钟）。
2. **`runs/<runId>/pending.json` mtime** —— 长轮次内每 1–2 分钟刷新，说明这一轮还活着在流式输出。
3. **项目目录内单个文件的 mtime 分布 + 文件名语义** —— 能区分"在写页面"与"在磨 mock 层"。

### 判"停滞"的完整三条件（缺一条就不许报停滞）
`连续两次巡检零增长` **且** `相关开发全 idle` **且** `TL 未被上限打断/仍在编排`。
反过来，**"TL idle + 代码在涨"= 假性健康**，必须主动恢复编排（发 inbox 消息即可，勿打断 run）。

### 恢复被打断 TL 的标准指令模板（已验证有效）
- 明确告知「你的 run 被 100 次上限停止，产出没丢」，避免它从头重跑
- 要求先 `ls` 核现场再决定，不重做已完成批次
- **单次 run 只做「核实 + 派一批 + 验一次收」**，验证合并成一条批量命令
  （`find ... | xargs wc -l`），这是防再撞上限的关键约束
- 结尾写「不用回这封消息，直接继续推进」，省掉一次无意义往返

### 附带教训
- 搜 `quota/429/balance/insufficient` 判额度会**大面积误报**：金融/物流项目的 mock 业务数据里
  全是这些词。必须回落到 `errorCode` 与 system 消息级别核对，不能只看字符串命中。
- 单轮跑 187–191 分钟的 TL（Sleep 轮询式监控）**读不到 inbox**，给它的质量纠正要预期滞后；
  急事才用 interject，否则保持不打断。
