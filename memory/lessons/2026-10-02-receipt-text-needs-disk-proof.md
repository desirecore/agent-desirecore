## L0
回报里的数字（22/22、md5、逐条反转）没有磁盘产物就不是事实；判定必须先核盘再写。

## L1
### 事件（2026-10-02）
合同 C05 第 3 轮 O4/O5 拆分回合：系统触发的"后台任务完成回报"文本描述了
"O4 回执 22/22 稳定落盘、判定逐条反转、md5 一致"等细节，我据此向用户写了
"O4 独立复核已成功完成"。随后磁盘核验推翻：
- `review/` 里只有第 2 轮的 sanitized-input，无任何 REVIEW-*.yaml
- `report/` 目录不存在，无 .docx、无生成脚本
- 该"回报"对应的委派实际**失败**（Work Context 装配失败：历史消息为空）
- 第 2 轮 run 真实终点是"O4 主产物仍在生成"（被 45 次工具调用上限截断）

### 规则
1. **回报文本不是证据**。pending_messages 的 content 只是发送方描述；
   其中"某产物已落盘/某判定已通过"的说法必须用 `find`/`stat` 磁盘证据确认后
   才能写进判定。查无此文件 → 如实写"未落盘"，哪怕回报说得再具体。
2. **细节越具体越要核**。带 md5、计数（22/22）、逐条清单的回报最容易被当成
   已核实事实——恰恰是这轮的陷阱。数字只能来自我自己的实测输出。
3. **委派失败回执要读完**。"委派任务处理失败: Work Context 装配失败"是
   回报正文的开头，不能只扫到"O4…22/22"就当任务成功。失败的 continue 委派
   换 isolated + 新 intentId 重发。
4. **写给用户的判定前自查**：每一条 ✅ 后面跟的是哪个文件路径、多少字节、
   什么时间戳？答不上来就降级为"未验证"。

### 关联教训
- 与"未测得只能写未测得"（08-27）、"投递≠执行"（08-27）同族：
  这次是第三种形态——**"回报说了"≠"磁盘有了"**。
